# PHẦN X — Dự án thực tế (Project LMS)

*Khi đi phỏng vấn, lý thuyết chỉ là phụ, 50% thời gian HR/TechLead sẽ hỏi xoáy vào project của bạn. Dưới đây là dàn bài chuẩn bị sẵn cho dự án **Spring Boot Learning Management System (LMS) - Quản lý học tập** mà bạn đang code trong máy.*

---

## 10.1. Giới thiệu dự án (Elevator Pitch)

> **Mô tả ngắn gọn & Súc tích (1 phút):**
> "Dự án của em là một hệ thống Quản lý Học tập (LMS) viết bằng framework Spring Boot. Hệ thống phục vụ việc quản lý các khóa học (Course), phân loại danh mục (Category), và cung cấp REST API cho người dùng xem danh sách cũng như tiến độ học tập. Em đảm nhận vai trò Backend Developer, code từ thiết kế database, viết REST API, xử lý mapping dữ liệu an toàn đến tối ưu các truy vấn JPA để tránh nghẽn cổ chai."

## 10.2. Kiến trúc & Công nghệ sử dụng

> - **Core**: Java, Spring Boot (cấu trúc chia Layer rõ ràng: Controller - Service - Repository).
> - **Database**: CSDL quan hệ giao tiếp qua Spring Data JPA.
> - **Thư viện phụ trợ ăn điểm**: 
>   - **Lombok**: Giảm code dư thừa (Boilerplate code).
>   - **MapStruct**: Framework giúp tự động map data từ Entity sang DTO siêu tốc, an toàn và tối ưu hơn các thư viện chạy lúc runtime (như ModelMapper).
>   - **Spring Validator**: Kiểm duyệt chặt chẽ (Validate) dữ liệu đầu vào.

## 10.3. Vấn đề/Bug khó nhất từng gặp & Cách giải quyết

> **Tình huống (Kể lỗi N+1 Query của JPA vì nó rất 'thực tế' và chứng tỏ bạn hiểu sâu bản chất ORM):**
> - **Vấn đề**: Khi em viết API trả về danh sách `Category` (mỗi Category chứa list nhiều `Course`), vì em cài đặt FetchType là `LAZY` (để tối ưu), nên lúc lấy dữ liệu mapping ra DTO, Hibernate tự động bắn ra thêm N câu query để lấy Course cho từng Category. Bảng có 100 Category thì hệ thống bắn 101 câu query xuống DB -> API chạy rất chậm.
> - **Khắc phục**: Lúc đầu em tính đổi thành `FetchType.EAGER` nhưng phát hiện nó lại gây chậm ở các luồng khác. Sau đó em tự viết Custom Query trong Repository, dùng từ khóa **`JOIN FETCH`** để ép DB gom tất cả lại thành đúng 1 câu lệnh `SELECT` duy nhất có kèm JOIN. Kết quả API phản hồi giảm từ vài giây xuống còn vài chục mili-giây.

## 10.4. Tối ưu hiệu năng (Performance Optimization)

> *Có thể chém thêm nếu Job Description yêu cầu kĩ năng tối ưu:*
> 1. **Áp dụng MapStruct**: Thư viện này gen ra code Java thuần (getter/setter) ngay lúc compile, nên tốc độ parse từ DB ra JSON nhanh hơn cực nhiều so với dùng Reflection.
> 2. **Chỉ dùng LAZY Loading**: Em rà soát và cấu hình 100% các quan hệ (OneToMany, ManyToOne) sang Lazy để không bao giờ bị load thừa dữ liệu rác lên RAM của Server.
> 3. **(Hướng phát triển / Chém gió thêm)**: Nếu hệ thống scale lên, em dự định áp dụng Redis Cache vào bảng `Category` vì dữ liệu danh mục khóa học thường user vào đọc thì hàng ngàn lần/ngày, nhưng admin cả tháng mới sửa 1 lần, bỏ vào Cache sẽ giảm tải tới 99% cho Database.

## 10.5. Các quyết định thiết kế (Design Decisions)

> Trả lời các câu hỏi dạng: "Tại sao em làm thế này mà không làm thế kia?"
> 
> **1. "Tại sao ở Controller lại phải tạo DTO, sao không trả thẳng cục Entity ra cho nhanh?"**
> - *Trả lời*: Entity chứa toàn bộ thông tin bảng DB (kể cả ID nhạy cảm, created_at) và đặc biệt chứa tham chiếu vòng (Category trỏ tới Course, Course trỏ ngược lại Category). Nếu trả thẳng Entity ra JSON dễ bị lỗi infinite loop (vòng lặp vô tận). DTO giúp em giấu thông tin DB, chỉ trả ra đúng những gì Frontend cần.
> 
> **2. "Em bắt lỗi (Exception) ở đâu?"**
> - *Trả lời*: Em không viết `try-catch` lẻ tẻ ở trong từng hàm Controller vì nó làm rác code và lặp lại liên tục. Em thiết kế 1 class `@RestControllerAdvice` (Global Exception Handler) để đứng ở ngoài cùng, hứng tất cả các RuntimeException từ tầng Service quăng ra. Sau đó tự động gói nó thành 1 format JSON chuẩn (có timestamp, message tiếng Việt, mã lỗi 400/404) trả về cho Frontend hiển thị. Đảm bảo mọi lỗi trả ra đều đồng nhất.
