## 8.1. Nguyên lý SOLID

> Bộ 5 nguyên tắc vàng trong OOP giúp thiết kế phần mềm dễ bảo trì và mở rộng:
>
> 1. **S - Single Responsibility (Đơn trách nhiệm)**: 1 class chỉ nên làm 1 việc duy nhất (VD: UserService chỉ lo logic tài khoản, không ôm luôn vụ gửi Email).
> 2. **O - Open/Closed (Mở để mở rộng, Đóng để sửa đổi)**: Thêm tính năng thì viết class mới (implements interface), không sửa đè lên code cũ đang chạy ổn định.
> 3. **L - Liskov Substitution**: Class con phải thay thế được class cha mà không làm hỏng app.
> 4. **I - Interface Segregation**: Đừng nhồi nhét quá nhiều hàm vào 1 interface khổng lồ. Hãy tách thành nhiều interface nhỏ chuyên biệt.
> 5. **D - Dependency Inversion (Đảo ngược phụ thuộc)**: Class cấp cao không phụ thuộc class cấp thấp, cả 2 nên phụ thuộc vào một Abstraction (Interface). -> Đây chính là tư tưởng cốt lõi của Spring DI.

## 8.2. Singleton Pattern

> Đảm bảo một class **chỉ có duy nhất 1 instance** (thực thể) được tạo ra trong suốt vòng đời ứng dụng, và cung cấp 1 điểm chung để truy cập nó.
> **Ví dụ**: Mặc định, mọi Spring Bean (`@Service`, `@Repository`) đều là Singleton.

```java
public class DatabaseConnection {
    private static DatabaseConnection instance;
    private DatabaseConnection() {} // Chặn new object từ bên ngoài
  
    public static synchronized DatabaseConnection getInstance() {
        if (instance == null) instance = new DatabaseConnection();
        return instance;
    }
}
```

## 8.3. Factory Pattern

> Khởi tạo đối tượng mà không để lộ logic khởi tạo phức tạp cho bên gọi, giao việc "nặn" object cho 1 nhà máy (Factory) xử lý bằng 1 hàm chung.
> **Lợi ích**: Dễ bảo trì và mở rộng. Khi thêm 1 loại object mới, chỉ cần sửa nhẹ ở class Factory, không cần đi khắp nơi sửa các lệnh `new`.

```java
// Khách hàng không cần new VNPAY() hay Momo(), chỉ cần ném String cho Factory
Payment p = PaymentFactory.getPayment("MOMO");
p.pay();
```

## 8.4. Builder Pattern

> Dùng để "xây dựng" một đối tượng rất phức tạp (có hàng chục thuộc tính) theo từng bước rõ ràng, thay vì nhồi hết vào 1 cái Constructor dài ngoằng dễ truyền sai thứ tự.
> **Ví dụ**: Annotation `@Builder` của thư viện Lombok.

```java
// Rõ ràng, dễ đọc, không sợ nhầm thứ tự các tham số như kiểu cũ: new User(1, "A", null, "B", true)
User u = User.builder()
    .id(1)
    .name("Ramen")
    .email("ramen@gmail.com")
    .build();
```

## 8.5. Strategy Pattern

> Bọc các thuật toán (chiến lược) khác nhau vào các class riêng rẽ có chung 1 interface. Khi chạy, chương trình có thể linh hoạt chuyển đổi qua lại giữa các chiến lược mà không cần viết câu lệnh `if-else` khổng lồ.
> **Ví dụ**: Tính giảm giá mùa lễ (Giảm 10%, Giảm tiền mặt 50k, Mua 1 tặng 1).

```java
public interface DiscountStrategy { double applyDiscount(double amount); }
public class TetDiscount implements DiscountStrategy { ... }
public class BlackFridayDiscount implements DiscountStrategy { ... }

// Truyền class giảm giá vào, code Checkout siêu sạch, không có chữ if nào
public void checkout(double total, DiscountStrategy strategy) {
    double finalPrice = strategy.applyDiscount(total);
}
```
